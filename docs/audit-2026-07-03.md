implementation maps to the intended conversion model, whether the
architecture should change, and the ordered path to completion.

re-prioritization, which [`completion-plan.md`](completion-plan.md)

## 2. How the code maps to the conversion model

The intended model — convert tiles/sprites and palettes first, remap
NES addresses to SMS-compatible ones, then convert instructions, sound
last — is exactly what is implemented:

1. **Assets** (`crates/assets`, `runtime/chrmap.s`, `runtime/ntmap.s`):
   NES 2bpp CHR → SMS 4bpp tiles, NES master palette → SMS 6-bit
   BBGGRR CRAM, NES nametable → SMS nametable format, 224-tile VRAM
   packing with software sprite flip variants (SMS has no flip bit).
2. **Address remapping** (`crates/analysis` memory classifier +
   fixed SMS RAM layout): every load/store is tagged (zero page,
   stack, RAM, PPU, OAM, APU, mapper, PRG data) and remapped — NES
   zero page → `$C000`, NES RAM → `$C200`, emulated 6502 stack →
   `$C100`, PPU/APU registers → runtime shim calls, PRG data reads →
   banked helpers.
3. **Instruction conversion** (`crates/ir` + `crates/lower` +
   `crates/z80_emit`): 6502 → semantic IR with explicit flags →
   conservative Z80 with a shadow 6502 status byte, bank-aware call
   trampolines, and a flag-liveness pass that elides dead flag
   updates.
4. **Sound last** (`runtime/apu_stub.s`): APU writes are logged to a
   ring buffer; the sound engine is stubbed behind 22 documented
   unresolved labels. Phase F does PSG mapping.

Verification exists at three layers: per-routine differential
validation (`oracle_6502` vs `z80_emu` on random input vectors),
whole-route semantic diff (`frame-diff`: NES reference RAM trajectory
vs SMS run over the same input script), and route acceptance with
framebuffer checkpoints (`trace-sms`).

## 3. Genericity check

Grepping the engine crates for SMB references finds only comments
using SMB as a motivating example — no `if smb` logic, no hard-coded
game addresses in `.rs` source. All 1,972 game facts (345 functions,
1,212 labels, 397 data regions, 18 jump-engine sites) live in
`profiles/smb.toml`. Principle 3 of the master plan is holding.

One structural caveat: the SMB profile was largely generated by
importing the doppelganger hand-made disassembly. The *engine* is
generic; the *profile authoring path* currently assumes a
community-quality disassembly exists. See gap G2.

## 4. Architecture verdict: keep it

No rewrite is warranted. The chosen architecture — static
recompilation with profile-driven discovery, a hand-written SMS
runtime shim for the hardware boundary, and layered differential
validation — is the same shape proven by N64Recomp/NESRecomp, and it
is demonstrably working here: an unmodified commercial NES ROM goes
in, a bootable SMS ROM comes out, and a scripted 1-1 clear completes
without any hand-ported game logic.

The alternatives are all worse:

- **Dynamic recompilation / interpretation on the Z80** cannot fit
  the SMS's 8 KiB RAM and 3.58 MHz budget.
- **Hand-porting per game** is exactly what this project exists to
  avoid, and the repo's own history (the retired `poc/` slice work)
  shows it stalls.
- **Restarting with a different IR or backend** would discard ~25K
  lines of tested code (374 tests) for no identified defect.

The wholesale approach (whole-ROM discovery → translate everything →
run full routes → fix by class of defect, never instruction-by-
instruction) is already the working method and should stay.

## 5. The three real gaps

### G1 — Real-emulator timing is unproven (biggest v1 risk)

All acceptance so far runs under `trace-sms`, which fires the frame
interrupt every **60,000 Z80 instructions**. Real SMS hardware
provides ~59,736 **cycles** per NTSC frame ≈ **~8,000–10,000
instructions**. The accepted route therefore enjoys roughly **6–8×
more CPU per frame than Mednafen or real hardware will give it**.
SMB runs its entire game loop inside the NMI handler; if a translated
frame takes 3–8 real frames, the game will run at a fraction of
speed (and input latching / sprite-0-style split timing may misbehave).

Nothing about this invalidates the correctness work — but it means
"plays in Mednafen" (the actual acceptance test) is not yet
demonstrated, and per-frame cost must be measured and then reduced.
The known optimization backlog (native-flag lowering behind the
existing liveness pass, inlining the hottest runtime helpers —
today's trace shows `rt_set_nz_a`-class helpers called hundreds of
thousands of times — LDIR loop lifting, cheaper far-call paths for
hot pairs) has not been started because correctness rightly came
first.

### G2 — Profile authoring assumes a hand disassembly exists

For "any NES ROM," discovery must reach high coverage without a
doppelganger-quality disassembly to import. The engine-side answer
is already planned but unbuilt: CDL ingestion (completion plan B.2 —
record a play session in Mesen/FCEUX, feed the code/data log to the
analyzer) plus jump-table target discovery from observed traces.
This is the difference between "SMB works" and "most NROM games
work," and it is also the honest test of principle 3.

### G3 — Deferred subsystems

Known and intentionally sequenced, not surprises: audio (Phase F),
non-NROM mappers (Phase I), post-1-1 visual correctness (raw-CIRAM
materializer, paused with documented rejection history), and the
small v1 visual polish items (floating sprite fragment, title-menu
clutter).

## 6. Re-prioritized path to completion

Ordered so each step de-risks the next; wholesale steps, no
micro-slices.

1. **Mednafen-in-the-loop verification (Phase G, now).** Get the
   generated ROM running under real Mednafen with reproducible input
   injection and frame capture (docker, headless). Compare captures
   against the existing checkpoint framebuffers. This is the user's
   stated acceptance test and directly measures G1. Emulicious as
   the second emulator afterward.
2. **Frame-budget measurement and performance program (G1).** Add
   per-frame instruction/cycle accounting to `trace-sms` (histogram
   of NMI cost per frame across the accepted route). Then burn down
   the worst offenders by class: native-Z80-flag lowering where the
   liveness pass proves it safe, inline the top runtime helpers,
   revisit far-call locality. Re-run the route after each class, and
   set the trace IRQ cadence to the real ~8–10K instruction budget
   once achievable — making the acceptance route timing-honest.
3. **v1 visual polish.** The remaining floating sprite fragment and
   title-menu clutter, validated against Mednafen captures rather
   than only the trace renderer.
4. **Audio (Phase F).** Decide the sound boundary (F.0), then APU
   event stream → PSG mapping. Closes the last 22 unresolved labels.
5. **Genericity proof (G2, Phase J.1 pulled earlier).** CDL
   ingestion, then a second NROM game (Balloon Fight or Ice Climber)
   through the pipeline with a profile built *without* a hand
   disassembly. Every SMB assumption that surfaces becomes an engine
   fix, not a profile hack.
6. **Broader SMB + mappers (v2/v3).** Full-game SMB (raw-CIRAM
   materializer resumes here), then UxROM/MMC1/MMC3.

## 7. What not to do (unchanged)

- No Rust-side hand-ports of game behavior.
- No SMB constants in engine source.
- No per-instruction trial-and-error; fix by defect class, verified
  by the differential harness and full-route runs.
- No claiming "playable" until it is playable in a real emulator at
  acceptable speed with a human on the controller.
